# Harness registry, local setups, and execution contracts

Lifecycle: evergreen component baseline.

This component implements `req-execution-configuration` REQ-3 and REQ-6 through REQ-11, `req-cli-authentication` REQ-3 and REQ-4, `req-delegated-execution` REQ-5, and `req-260821-830dbf` REQ-3 and REQ-6. It owns the harness definition and its validation, the client-local execution setup file and every CLI act over it, harness probing, and the launch environment a harness child receives from `conveyor run` or the worker loop. `component-work-orders` owns claim, lease, release, and the supervision of the running child; `component-git-delivery` owns the task worktree and the forge boundary; `component-mcp-protocol` owns the run-order routes; `component-runtime` owns `cmd/conveyor/main.go`, which wires the commands named here.

## A harness is data, not an adapter

A harness is one entry in the `harnesses` list of the local execution document, decoded into `config.Harness` (conveyor:internal/config/config.go:266-282). `command` is an argv array that is never shell-evaluated; placeholders substitute as whole argv elements (conveyor:cmd/conveyor/worker_cmd.go:2458-2483). `validateHarness` enforces the field-local rules (conveyor:internal/config/config.go:1790-1878):

| Field | Rule |
| --- | --- |
| `command` | exactly one `{prompt}`; exactly one `{mcp_config}` for `json_file` and `toml_override`, none for `environment` |
| `resume_command` | optional; when present exactly one `{session_id}` and no other placeholder |
| `model_args` | only `{model}`; appended only when a model resolves |
| `effort_args` | `low`, `medium`, `high` to literal argv; a harness with no entry declares no effort |
| `probe_command`, `probe_timeout` | required, placeholder-free; positive duration |
| `stall_timeout` | default 10m; literal `0` disables it, the one accepted non-positive value |
| `mcp_attachment` | required for `environment`, forbidden otherwise; `^[A-Za-z0-9][A-Za-z0-9._-]{0,62}$` |

An `environment` harness is rejected when any field contains `CONVEYOR_ADDR`, `CONVEYOR_API_TOKEN`, `CONVEYOR_SESSION_ID`, `CONVEYOR_CLIENT_TOKEN`, `Bearer `, a URL with user info, or a query key containing TOKEN, SECRET, KEY, or AUTH (conveyor:internal/config/config.go:1886-1926; AC-3.1). `config.ValidateHarness` repeats the rules on the worker before probe or launch.

`config.HarnessTemplates` is the ordered built-in catalog: Codex (`codex exec`, `toml_override`), Claude Code (`claude -p`, `json_file`, stream-json, `--resume {session_id}`), Grok (`grok --single`, `environment`), Cursor (`cursor-agent -p`, `environment`, `--resume {session_id}`, no effort argv) (conveyor:internal/config/harness_templates.go:15-103). `conveyor init` and the non-interactive setup path take the first entry as the default (conveyor:cmd/conveyor/init.go:265; conveyor:cmd/conveyor/execution_setup.go:648). Headless permission grants are launch data inside template argv: Claude `--permission-mode bypassPermissions --allowedTools mcp__conveyor__*`, Grok `--permission-mode bypassPermissions`, Cursor `--force --trust` (AC-3.2). Changing a template never rewrites an existing local file.

## MCP transports keep secrets out of argv

`prepareMCPConfig` renders `{mcp_config}` per transport (conveyor:cmd/conveyor/worker_cmd.go:2319-2340). `json_file` writes `mcp.json` at mode 0600 into the attempt's temp directory, removed when the attempt returns (AC-3.3). `toml_override` produces one TOML expression naming `bearer_token_env_var="CONVEYOR_API_TOKEN"`. `environment` substitutes nothing: the harness finds Conveyor in its own configuration through `${CONVEYOR_ADDR}` and `${CONVEYOR_API_TOKEN}`, and the launcher sets `CONVEYOR_ADDR` to the server base plus `/mcp` (conveyor:cmd/conveyor/worker_cmd.go:1096-1099).

An `environment` launch fails closed unless readiness proves the registration (AC-3.4). `validateEnvironmentAttachment` dispatches on the command basename (conveyor:cmd/conveyor/grok_mcp.go:62-74). For `grok` it runs `grok inspect --json` and `grok mcp doctor <attachment> --json` under the child environment and requires an `http` server named by `mcp_attachment` whose `config.toml` source carries exactly `url = "${CONVEYOR_ADDR}"` and `Authorization: Bearer ${CONVEYOR_API_TOKEN}` (conveyor:cmd/conveyor/grok_mcp.go:78-171). For `cursor-agent` it runs `cursor-agent mcp list-tools <attachment>` and requires the five lifecycle tools `claim_work_order`, `renew_work_order`, `release_work_order`, `submit_for_review`, and `submit_review_verdict` in the listing (conveyor:cmd/conveyor/grok_mcp.go:187-240). Any other basename declaring `environment` fails launch. Readiness never creates or repairs the harness's own configuration.

## Native MCP registrations and stored credentials

The explicit `conveyor mcp install` act owns persistent personal-client registrations under `req-cli-authentication` REQ-4. It does not own the temporary registration or credential a worker or run launcher gives its child. The launch transports and readiness rules above continue to apply without modification. In particular, installation must not replace an environment-based worker attachment with access to the operator's saved personal credential.

### Server identity and registration names

Installation selects the saved credential for the canonical server named by `--server`, then `CONVEYOR_ADDR`, or the sole stored server when neither is present. More than one stored server requires explicit selection. No stored credential means refusal before a write.

Canonicalization uses the same `normalizeServerURL` contract as login: lowercase scheme and host, reject user info, query and fragment, strip trailing slashes and one terminal `/mcp`, and retain the base path and explicit port. It does not equate explicit and implicit default ports or distinct base paths. Installation must not create a different credential-key normalization from login. The endpoint is the canonical base plus `/mcp`.

The default registration name is `<host-slug>-<identity-hash>-conveyor`. The host slug lowercases the hostname, replaces runs outside ASCII letters and digits with a hyphen, trims hyphens, and truncates to 30 characters; an empty slug becomes `server`. The identity hash is the first 12 lowercase hexadecimal characters of SHA-256 over the complete canonical URL, including scheme, explicit port, and base path. Thus selection order does not affect naming. A hash collision with a different endpoint is a refusal, never a repoint.

`--name` provides an explicit registration name. It trims surrounding whitespace, lowercases ASCII letters, and accepts only `[a-z0-9][a-z0-9_-]{0,62}`; it rejects other input rather than silently merging distinct spellings. An explicit name such as `funnelflux-conveyor` is supported. If exactly one owned registration already identifies the selected server, a reinstall without `--name` reuses that name. Multiple owned matches are ambiguous and require a name. A requested name that belongs to a different server, including an owned entry, is refused. A requested second name for the same server requires an explicit owned-entry rename, preserving its policies, and never creates a duplicate implicitly.

### Credential references by client

The token-print bridge remains the single supported stored-credential output surface (`req-cli-authentication` AC-2.3 and AC-4.2). Extend `conveyor auth token --server <canonical-base>` with `--format http-headers`, which emits only a JSON object containing the Authorization bearer header on its private stdout pipe. The ordinary form retains its existing raw-token output. Both read the selected saved credential afresh, never substitute the ambient `CONVEYOR_API_TOKEN`, and never log their output. This explicit credential-output act is not an installation diagnostic.

Codex uses its native `http_headers_helper` with the canonical endpoint and an invocation of the installed Conveyor binary's header-format token bridge. Claude uses its native `headersHelper` with the same bridge and `type: http`. The installer resolves the Conveyor executable to an absolute path, serializes the helper in the client's accepted shape, and correctly quotes any client-required shell command. It creates no user-authored helper script. Only the executable path, canonical server and format selector enter editor configuration; no token enters arguments, configuration, installation output or logs. Any nondefault credential-store location must be conveyed through a supported non-secret configuration reference so a desktop launch resolves the same store as login.

The installed-client parser and a controlled native connection must demonstrate the helper field is honored; acceptance of an unknown field alone is insufficient. Unsupported client versions produce a clear upgrade or connection-check result, never a false claim that the saved credential is bound. The local Codex helper contract is documented in [OpenAI's MCP reference](https://learn.chatgpt.com/docs/extend/mcp?surface=cli); Claude's is documented in [its MCP reference](https://code.claude.com/docs/en/mcp#use-dynamic-headers-for-custom-authentication). These are adapter-schema references, not authority to change Conveyor's credential boundary.

Cursor and OpenCode use their supported HTTP environment-reference mechanism with a separate variable `CONVEYOR_MCP_TOKEN_<full-uppercase-SHA256-of-canonical-URL>` for every server. Their URLs are literal canonical endpoints, not a shared address variable. Cursor headers use `${env:NAME}`; OpenCode headers use `{env:NAME}`, its type remains `remote`, and its personal-access-token registration disables automatic OAuth. Installation prints a correctly shell-quoted export assigning that variable from `conveyor auth token --server <canonical-base>`. It never prints the result of that command, writes a shell profile, or writes a token-bearing environment file. These clients require an environment containing their individual variables; setup output must say so and must not claim desktop retrieval without that setup. Client syntax is described by [Cursor](https://cursor.com/docs/mcp) and [OpenCode](https://opencode.ai/docs/mcp-servers/).

Helper execution reports missing credentials without a value and reads rotations on its next invocation. Native clients may cache helper results; setup guidance distinguishes the client's refresh behavior from a restart. Environment-reference clients need their server-specific export refreshed and their client restarted after rotation. A native authentication rejection reports the selected server and credential source, names login or refresh as the remedy, and does not switch credentials. Revocation is enforced by the server on use. Installer reconciliation refuses conflicting manual Authorization or OAuth sources rather than silently allowing them to override the selected saved credential.

The ordinary CLI precedence remains explicit flag, server-bound environment token, then saved credential. `CONVEYOR_API_TOKEN` applies only to the normalized environment server or the localhost default when the environment server is absent (`req-cli-authentication` AC-1.4). Worker/run child credentials, cleanup, redaction, and existing environment readiness are unchanged by personal-client installation. A legacy registration whose shared environment endpoint cannot be bound unambiguously to the selected saved server is not automatically migrated.

### Ownership, migration, and publication

The targets remain Codex's user config, Claude's user config, Cursor's global MCP config, and OpenCode's config under an absolute XDG_CONFIG_HOME or the platform's existing fallback. `--tool` selects one adapter. `--list` performs only read-only reconciliation: it writes no config, staging file or credential and runs no credential helper or native connection.

Recognize only existing installer markers: the exact Codex owner comment adjacent to the entry, the legacy Claude/Cursor root marker for the legacy `conveyor` member only, and OpenCode's in-entry owner marker. A legacy root marker does not confer ownership of other members. New ownership metadata identifies each managed registration and canonical endpoint. Keep OpenCode's ownership inside its entry; do not add unknown top-level keys. Use comments or accepted metadata surfaces for other clients and validate generated configuration against the installed parser.

Migrate a uniquely identified owned legacy `conveyor` entry to the selected server name while preserving unknown fields, nested tool policies, enablement and timeouts. Move Codex nested per-server tables with the entry, preserving their contents. A conflicting destination, ambiguous source endpoint, duplicate member or unsupported syntax fails before publication. An unmarked/manual entry remains unchanged unless `--adopt` explicitly addresses that entry and its endpoint matches the selected server. Adoption does not authorize repointing a different server. Legacy environment-based Cursor/OpenCode entries need an unambiguous endpoint binding and explicit adoption before changing a potentially worker-consumed attachment.

Reconciliation changes only installer-owned transport, credential-reference and ownership fields after checking manual conflicts; it preserves unrelated entries and user policies. Reinstalling either of two servers leaves the other's configuration and credentials unchanged. Files are published atomically through an owner-only temporary file, with safe-path and symlink checks before staging and publication. Resulting editor files remain owner-only. A failed parse, collision or validation leaves original bytes and permissions unchanged.

OpenCode retains its staged `opencode debug config` check: validate a separate copy in the same directory so relative references keep their meaning, isolate HOME/XDG and project configuration, give placeholders for required environment references, bound execution to 30 seconds, discard stdout, and return non-secret errors. Never publish the copy a client may rewrite. Refuse comments when they cannot be preserved. If an explicitly selected client is absent, report parser validation as skipped; skipped validation is not native connection evidence.

### Connection reporting, plugin setup, and verification

Report registration name, endpoint, credential source, config path/write result, parser result, client restart requirement, and native initialization/tools-list result as separate facts. A parser check proves only configuration acceptance. A native check must use the generated registration and the supported client's actual MCP runtime, initialize successfully, and obtain tools/list from a controlled fixture. Direct generic HTTP probing never proves a native client is blocked or connected. A genuine external denial is an operator checkpoint; it does not authorize a proxy bypass, relaxed TLS, altered Cloudflare policy, or production credential exposure.

The shipped plugin must not auto-register an unrelated localhost connection that appears to be an installed remote server. Distribute connection-neutral operator guidance and direct setup to the named native registration. Document removal or disabling of legacy plugin connections separately from migrating installer-owned personal entries. The create_task guidance must follow the served schema: require body/repository/idempotency data as applicable, omit caller-supplied title and retired execution mode, and preserve all operator gates. Coordinate setup-only edits to docs/mcp.md with its tool-inventory owner.

Fixture verification covers distinct saved credentials at two servers, both reinstall orders, explicit names and collisions, ports and base paths, unrelated environment credentials, missing/rotated/revoked credentials, nested policies and adoption boundaries, symlink refusal, atomic failures, permissions, read-only listing, installed parser acceptance, and a controlled native initialize/tools-list exchange. Secret markers in runtime fixtures must never appear in generated files or diagnostics. Record actual client versions and distinguish unavailable native binaries from passed checks. Run the focused MCP/auth tests through Make and the complete `make test` aggregate under `component-verification-strategy` and DEC-29. No database schema or HTTP tool inventory changes are required.

Credentials and default workspace remain per server in the existing owner-only credentials file. This section changes personal MCP installation and narrowly required token-print formatting only; it does not change login storage, token issuance, task gates, assignment, priority, phase, worker authority, or propose-confirm rules.

## Setups are named contracts on the client

The local execution document is `conveyor.yaml`, resolved from `--config`, then `CONVEYOR_CONFIG`, then a file in the working directory, then `<user config dir>/conveyor/conveyor.yaml` (conveyor:cmd/conveyor/execution_config_path.go:28-50). `config.Load` rejects unknown fields and normalizes. A document carries `harnesses`, a `setups` list, and `default_setup`; each `ExecutionSetup` names spec, implementation, optional verify, and review settings, an ordered review panel, and `refresh_review` (conveyor:internal/config/config.go:426-432). Names must be one path-safe segment and unique; every setup normalizes independently against the shared harness list, so a route or seat naming an unregistered harness fails the load; the top-level `execution_settings` and `review` members are a read-only projection of the default (conveyor:internal/config/config.go:1073-1143). `Setup(name)` resolves an empty name to the default and never falls back for an unknown name (conveyor:internal/config/config.go:1699-1722).

`loadNamedLocalExecutionSetup` is the one loader for `conveyor run` and the worker: it loads the file, projects the chosen setup with `WithSetup`, validates the worker document, and resolves `first_activity_timeout`; a failure names the path and `conveyor config init-execution` (conveyor:cmd/conveyor/execution_setup.go:38-63). The same file sets `worktree_root`: `~` expands against the home directory, a relative value is rejected, and omission means `~/.conveyor/worktrees` (conveyor:internal/config/config.go:1200-1205, 1985-1990).

The acts are `conveyor setup create|edit <name>` (interactive; create refuses an existing name, edit is prefilled), `conveyor setup list` (per-stage harness, model, effort, timeout, ordered seats, default marker), `conveyor setup default <name>`, `conveyor setup delete <name>` (refuses the default and the last setup), `conveyor setup seat add|remove|move` (append a probed seat; remove or move by one-based position), and `conveyor config set [--setup <name>] execution.<stage>.<field> <value>`, where the field is harness, model, effort, or timeout, `review.seat.<n>.<field>` addresses one seat, and a bare key targets the default (conveyor:cmd/conveyor/named_execution_setup.go:21-173, 214-273, 447-519). Existing-file mutations decode the authored YAML into nodes. The shared writer compares the normalized configuration before and after the requested mutation and applies only those differences to the authored nodes (`marshalAuthoredExecutionConfig` in conveyor:cmd/conveyor/execution_setup.go). Normalized defaults and derived projections are comparison inputs; the writer does not serialize them into untouched fields. Bare keys use the same named-setup mutation path with the default setup selected (AC-10.2, AC-10.6). Setting a harness selects the template by name and probes it before saving.


The node editor preserves key order, comments, scalar styles, and authored omissions. It retains aliases when their final values still match a preceding anchor. When editing one alias consumer would change another setup, the writer materializes that consumer independently; merge-inherited values receive local overrides. Named setup and harness sequences match by name, while unchanged review seats retain their nodes when moved. A default-setup field edit updates the same field in an existing top-level projection. An omitted top-level projection stays omitted. An explicit default switch copies the selected setup's authored settings and review panel into the top-level projection. Legacy singleton files remain singletons until setup creation requires a named list.

Review harness, model, and effort acts update the addressed seat, with `execution.review.<field>` selecting seat one. They leave non-empty `fallback_harness` and `fallback_model` unchanged. Empty fallbacks stay empty when explicit seats make them unnecessary; a fallback may be populated only when it is empty and required for validation. Wizard edits change captured stage choices, review timeout, and seats while retaining planning settings, existing model policy for unchanged models, refresh policy, and review fallbacks. New-file bootstrap and setup creation still produce complete valid setup documents.

The writer marshals the edited node document to the existing temporary-file publication path, reloads it through `config.Load` and `validateWorkerConfig`, and publishes it by rename at mode 0600. A failed validation leaves the original file unchanged. In-memory `config.Load` normalization, harness validation and probe-before-save, server policy projection, and workspace writes retain their existing behavior. Raw-YAML regressions in `cmd/conveyor/config_set_roundtrip_test.go` compare all persisted values and exercise both key forms, fallback preservation, wizard/default/seat mutations, aliases, merge keys, permissions, and publication failure. The complete local Make gate follows `component-verification-strategy` and DEC-29.
## The interactive creation flow and its twin

`conveyor config init-execution` and `conveyor setup create` run one `huh` form (DEC-30). Without a terminal the command exits naming the `conveyor config set execution.<stage>.<field>` twin (AC-9.2). Detection keeps each template whose probe binary is on PATH and probes them concurrently; only detected harnesses are offered, and an unhealthy one is labelled with its probe message and rejected by field validation (conveyor:cmd/conveyor/execution_setup.go:233-257, 375-396).

The groups are: one confirmation that accepts the first healthy harness with suggested models, effort, timeouts of 30m, 4h, and 1h, and one review seat (AC-9.5); one group per stage holding harness, model, effort, and timeout (AC-9.4); the review group with its timeout and each seat's fields; a seat group whose actions are add, remove, move earlier, and move later, chosen by selection (AC-11.4); and a summary whose decline returns to editing with values intact (AC-9.7) (conveyor:cmd/conveyor/execution_setup.go:113-231, 287-322, 412-449). A seat action re-runs the form with the seat list changed. `--defaults` writes the defaults without a terminal (AC-9.9). Persisting merges the selected harnesses into an existing file and updates its default setup, or writes a new document (conveyor:cmd/conveyor/execution_setup.go:472-584). The wizard has no HTTP client (AC-9.8).

## Freezing and the attempt boundary

The server persists pipeline policy only. `PolicyDocument` clears execution settings, routing, harnesses, setups, planning models, and seat contents, and `ExecutionSetup.MarshalJSON` emits only `max_bounces`, `stage_timeouts`, the seat count, and `refresh_review` (conveyor:internal/config/config.go:437-458, 1658-1672). `FreezePolicy` projects that subset into the task contract at intake and `WithPolicy` overlays a frozen contract without touching local execution detail (conveyor:internal/config/config.go:1676-1695, 1750-1780; DEC-23; REQ-7, REQ-8). The retired task-setup endpoint remains unavailable; VERIFY-HTTP-1 defines the policy-only operator exception.

Local execution freezes at the attempt. `conveyor run` loads the setup once before its first claim (conveyor:cmd/conveyor/run_cmd.go:202-217). The worker reloads the file on every loop iteration and hands the loaded config to the child goroutine, so an edit applies to the next claim and never to a launch in flight (conveyor:cmd/conveyor/worker_cmd.go:429-509; `req-delegated-execution` REQ-5). A released order's pinned server snapshot is re-resolved against the current registry and kept when unchanged (conveyor:internal/worker/service.go:1195-1213; AC-5.1).

## Snapshots, fingerprints, and heartbeat probes

A work order may carry `required_model`, `required_harness`, `required_effort`, and `required_harness_config` (conveyor:internal/core/types.go:673-676); the worker logs their presence and uses the local setup (conveyor:cmd/conveyor/run_cmd.go:774-785). `HarnessFingerprint` hashes name, transport, attachment, command, model args, sentinels, effort args, probe command, probe timeout, and stall timeout; `resume_command`, addresses, and tokens are outside the hash (conveyor:internal/worker/service.go:172-192; AC-5.2). The server's `ActiveHarnesses` lists the snapshot of every queued or claimed spec, implement, verify, or review order, and the worker heartbeat probes the union of its local harnesses and those targets, keyed by name and fingerprint (conveyor:internal/worker/service.go:334-360; conveyor:cmd/conveyor/worker_cmd.go:698-721). A healthy probe repeats every minute; an unhealthy one retries from 5s doubling to 1m, and a health change is reported once as a transition (conveyor:cmd/conveyor/worker_cmd.go:369-373, 723-783). A healthy result needs a fingerprint and a non-empty message. Serviceability derived from heartbeats is advisory and liveness-only (REQ-6).

## Named defaults and review seat resolution

Defaults: policy stage timeouts spec 30m, implement 4h, review 1h; `first_activity_timeout` 2m, which must be shorter than every MCP stage timeout; harness `stall_timeout` 10m; `max_bounces` 10; `work_order_queue_timeout` 24h; `worktree_root` `~/.conveyor/worktrees`; implement and review concurrency 1 each (conveyor:internal/config/config.go:324-332, 780-793, 1236-1257).

`selectLocalExecutionDispatch` takes harness, effective model, and effort from the stage route, then lets the review seat at the order's one-based index override each it names (conveyor:cmd/conveyor/run_cmd.go:787-825; REQ-11). A review order whose seat index exceeds the configured seat count is a capacity shortfall before any claim: an attended run prints the required and configured counts and claims nothing; the worker logs the same counts and leaves the order queued (conveyor:cmd/conveyor/run_cmd.go:219-229; conveyor:cmd/conveyor/worker_cmd.go:484-491, 544-551; AC-11.2, AC-11.5). `conveyor run --setup <name>` projects that setup for the invocation, probes its harnesses before the first claim, and leaves the default untouched; an unknown name lists the configured names (AC-10.4, AC-10.8). The worker always uses the default (AC-10.9) and claims within its per-stage concurrency limits (conveyor:cmd/conveyor/worker_cmd.go:452-483).

## The client-local execution boundary at launch

Before enrollment or claim, both entry points load the setup and check `GET /v1/forge-token`, failing with the named remedy when no token is stored (conveyor:cmd/conveyor/worker_cmd.go:394-407; conveyor:cmd/conveyor/run_cmd.go:68-73; conveyor:cmd/conveyor/forge_token_preflight.go:14-25). The worker's enrollment credential comes from `CONVEYOR_WORKER_TOKEN` or `<user config dir>/conveyor/workers/<workspace>.json`, written 0600 after a pairing exchange (conveyor:cmd/conveyor/worker_cmd.go:98-158). `conveyor worker install` writes a per-user launchd or systemd unit carrying only `CONVEYOR_ADDR`, `HOME`, and the config path (conveyor:cmd/conveyor/worker_service.go:206-309, 339-403).

For `conveyor run` the parent keeps the personal access token and issues a session-bound agent credential for the child, revoked on every return path; a worker child receives the enrollment credential (conveyor:cmd/conveyor/worker_cmd.go:922-939). The child environment replaces exactly these inherited values: `CONVEYOR_API_TOKEN`, `CONVEYOR_ADDR`, `CONVEYOR_WORKSPACE`, `CONVEYOR_WORK_ORDER_ID`, `CONVEYOR_SESSION_ID`, `CONVEYOR_CLIENT_TOKEN`, `CONVEYOR_WORKTREE_ROOT`, the branch assignment `CONVEYOR_TASK_ID`, `CONVEYOR_TASK_BRANCH`, `CONVEYOR_TASK_BASE_BRANCH`, `CONVEYOR_TASK_REPO`, `CONVEYOR_TASK_REPO_URL`, and the attempt continuity values `CONVEYOR_CURRENT_ATTEMPT_ID`, `CONVEYOR_PREVIOUS_ATTEMPT_ID`, `CONVEYOR_PREVIOUS_ATTEMPT_REASON` (conveyor:cmd/conveyor/worker_cmd.go:1100-1126, 2342-2362). A spec order runs in a fresh depth-1 clone made read-only with pushes disabled; other stages run in the verified primary checkout from `repos[].checkout` or the launcher's directory (conveyor:cmd/conveyor/worker_cmd.go:564-607, 2105-2135).

Argv is `command` with placeholders replaced, then `model_args`, then the effort argv (conveyor:cmd/conveyor/worker_cmd.go:1063-1095). When the order is server-eligible for continuation, the harness declares `resume_command`, and the harness name and launch environment match, the client appends the resume argv with the stored session id and prepends operator direction to the prompt; a resume start failure retries cold (conveyor:cmd/conveyor/continuation.go:33-75; conveyor:cmd/conveyor/worker_cmd.go:1242-1246; DEC-24). Every harness with `resume_command` has its stdout watched for the first `{"type":"system","subtype":"init","session_id":...}` line, reported as continuation metadata (conveyor:cmd/conveyor/continuation.go:89-152). Child output passes through an exact-match redactor holding the parent credential, child credential, address, session id, client token, and locally supplied Git token (conveyor:cmd/conveyor/worker_cmd.go:1189-1211). `first_activity_timeout` and `stall_timeout` bound the child; their enforcement belongs to `component-work-orders`.

## Executing-user git authorship and credentials

Every dispatch carries the executing user's display name and email from run ownership or worker enrollment ownership; an incomplete identity fails the dispatch listing (conveyor:internal/worker/service.go:581-586; conveyor:internal/httpapi/run.go; conveyor:internal/store/actor.go:91-99). The launcher copies both into `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME`, and `GIT_COMMITTER_EMAIL` (conveyor:cmd/conveyor/worker_cmd.go:1121-1126; `req-260821-830dbf` AC-3.3).

Worker and run credentials resolve through one invocation-local resolver in `cmd/conveyor/local_git_credential.go` (`req-260821-830dbf` REQ-6, AC-6.1 through AC-6.3; DEC-33). `CONVEYOR_GIT_TOKEN`, read from the startup environment, selects the explicit path. The token reaches Git through the existing self-askpass variables in the child environment, with credential helpers disabled and an HTTPS remote without user info. It never enters argv, on-disk Git configuration, or a credential store. The startup variable itself is omitted from the child environment. When it is unset, the launcher adds no askpass or credential-helper overrides, and Git resolves the host's ambient credential.

After the stored-token presence check, both entry points check the task repository before claiming. The shared preflight runs `git ls-remote --heads <repository URL> <base branch>` under the same Git environment as the child, adds `GIT_TERMINAL_PROMPT=0`, and bounds the command to twenty seconds. It uses the verified primary checkout for non-spec stages. Each invocation caches success and failure by repository URL; a worker skips failed items without claiming or changing queue position. The refusal names both remedies: set `CONVEYOR_GIT_TOKEN`, or configure the host's Git credential for that host. Restarting the invocation refreshes the cache. This read check establishes repository access, not write permission; a later push can still fail.

The shared client scrubber removes the exact locally supplied value from captured output before transcript spooling, activity and failure tails, checkpoint bodies, or TUI fanout. A streaming wrapper retains incomplete token prefixes across writes and newlines before the existing session redactor runs. The common worker/run HTTP request boundary scrubs JSON strings, including escaped values and evidence bodies, before upload. Local diagnostics use the same scrubber. No unredacted local token is persisted in snapshots or transcript files. Claim, renewal, reconciliation, checkpoint, and release responses carry no stored token value.

## CF-H1: Deliver and present artifact-context freshness

This section implements `req-delegated-execution` v4 REQ-5, `req-260802-72fc68` v2 REQ-2 and `req-security-boundaries` v6 REQ-1/REQ-4. The work-order service in CF-W1 through CF-W4 owns freshness state and the MCP protocol in CF-M1 owns refresh transport. Launchers preserve the selected persisted default_setup and the harness/model/effort frozen on an active attempt; freshness is not harness configuration.

Worker and task-run delivery forward the shared context_freshness envelope with its exact selection revision and claim-bound artifact references to the child. Metadata delivery means available, not fetched. A launcher presenting a progress message or polling proposals never acknowledges an artifact. The child may explicitly refresh through the native claim-bound tool before subsequent artifact reads; lifecycle submission performs the bounded refresh even when an older child omitted that call. New context is discoverable within the same claim through this pull protocol; this revision promises no unsolicited push into an already-running model turn.

The existing task-scoped run-order projection, adaptive proposal polling, gate actions, non-TTY behavior and cancellation remain unchanged. It provides exact IDs within the envelope's existing bounded descriptors. Unchanged repeated receipts do not flood attended output. It adds no independent workspace poll, acknowledgement prompt or lifecycle wait. Raw machine-readable output retains the structured envelope under existing redaction.

For in-process delivery, the dispatcher uses the same selection function and records available metadata when constructing context. It records fetched only for complete artifact bodies actually admitted to the provider-input boundary. A failed byte read, body omitted by input budget, or truncated body has its own fixed diagnostic; none counts as fetched. A provider-input boundary observation proves neither successful transport to the provider nor model understanding. Pre-verdict refresh returns the same nonblocking summary and does not introduce an extra unbounded provider loop.

Selection fingerprints exclude delivery observations, actor/session, wall-clock time, credentials and model-run counters. Fetching a correction changes its observation state without changing the same selection fingerprint; this prevents a self-invalidating refresh loop. All summaries preserve provenance and untrusted-data framing and keep authority reference changes separate from immutable governing pins. No child gains operator confirmation, recovery or merge capability.
